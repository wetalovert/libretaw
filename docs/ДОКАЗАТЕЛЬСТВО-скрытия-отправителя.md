# Доказательство: скрытие отправителя от сервера (этапы A и C)

Этот документ показывает, что именно проверено, как воспроизвести проверку и что **не** доказано.

## 1. Серверная проверка на настоящем сервере

Команда: `node tests/proof-sealed.js`. Скрипт запускает сервер, подключает получателя, отправителя и анонимное подключение, отправляет обычное и запечатанное сообщения, и считает вхождения идентификатора отправителя в кадрах, очереди, файлах данных и журнале сервера. Контроль: обычное сообщение от того же отправителя должно содержать его ID (иначе поиск не работает).

```
| Проверка | Найдено | Ожидаемо |
|---|---|---|
| CONTROL ordinary message, frames to recipient | 1 | >0 | OK
| SEALED message, frames to recipient | 0 | 0 | OK
| SEALED message, frames delivered carry a recipient-visible sealed packet | 1 | >0 | OK
| SEALED message in offline queue (delivered later), message frames | 0 | 0 | OK
| KNOWN LEAK (not closed): sender id in presence list (online users) | 2 | не закрыто | известно
| SEALED test: sender id on disk (files under data dir) | 0 | 0 | OK
| SEALED test: sender id in server log | 0 | 0 | OK

ВЫВОД: отправитель не виден в запечатанных сообщениях; контроль подтверждает, что поиск работает.
```

Что это значит:
- В кадрах **сообщений** запечатанного отправления ID отправителя нет. Контроль (обычное сообщение) содержит его, поэтому поиск работает.
- Запечатанное сообщение, доставленное позже из очереди, тоже без ID отправителя.
- Строка «KNOWN LEAK» — **не закрыта**: список онлайн-пользователей (presence) рассылается всем подключённым и содержит ID отправителя. Запечатывание сообщений эту утечку не убирает.
- Проверка файлов на диске здесь почти ничего не доказывает: данные на диске зашифрованы паролем сервера, поэтому идентификатор в них не найти и без проверки. Доказательством служит путь кода: поле `src` в доставке запечатанных сообщений всегда пустое.

## 2. Сервер: тесты поведения

```
  ok   recipient receives the sealed message
  ok   the delivered packet has no sender and no recipient field
  ok   the sender identity appears nowhere in the delivered frame
  ok   a sealed message without the work proof is dropped
  ok   an anonymous connection cannot send an ordinary message
  ok   spoofing the sender on an authenticated connection is still refused
  ok   a queued sealed message is delivered later without a sender
  ok   the sender is not stored in the offline queue

result: 8 passed, 0 failed
```

Проверено: получатель получает запечатанное сообщение без отправителя; сообщение без вычислительной задачи отбрасывается; анонимное подключение не отправляет обычные сообщения; подделка отправителя на обычном подключении отбрасывается; офлайн-очередь хранит без отправителя.

## 3. Браузер: что уходит на сервер

Проверено в браузере полным путём `lanSend → e2eSeal → sealOut`, с перехватом всех отправляемых пакетов:
- отправлена **одна** посылка на сервер через анонимное подключение, адресат — получатель;
- ID отправителя, его имя и текст сообщения в посылке **отсутствуют**;
- посылка содержит только поля оболочки: `sv`, `eph`, `iv`, `ct`, `pow`, `to`.

## 4. Криптография

Оболочку открывает только получатель. Сторонний ключ её не открывает. Проверено в браузере.

## Что НЕ доказано

- **Пакеты в LAN.** В проверке браузера тестовый пир не попал в список открытых соединений, поэтому пакеты LAN не перехватывались. Структура пакета LAN та же, что и у серверного, но перехват LAN в этом прогоне не выполнен.
- **Сквозная проверка на двух устройствах.** Не проводилась: телефон и компьютер через настоящий сервер.
- **Сетевой адрес отправителя.** Сервер видит IP-адрес анонимного подключения и время отправки. Это не скрыто и не проверялось.
- **Presence.** Утечка известна и не закрыта.
- **Группы, каналы, карточки профиля.** Не входят в этап A.

## Как воспроизвести

```bash
node tests/proof-sealed.js     # серверные кадры, очередь, журнал
node tests/svtest.js           # поведение сервера (8 проверок)
```
Браузерная проверка описана выше; для её повтора откройте страницу, создайте аккаунт и выполните перехват `svAnonSend` и `lanRaw` во время вызова `lanSend`.
